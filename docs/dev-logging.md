# Диагностические логи и разбор разрывов

Логи пишутся в `cache/logs/fog-YYYYMMDD.jsonl` (7 дней, 2 МБ на день) и нужны
для одного вопроса: **почему запись трека пропала**. С change
`fix-track-gap-visibility` лог отвечает на него сам — каналом `LIFE`.

## Формат строки

```
ts_wall|ts_mono|session|seq|tag|level|msg|payload_json
```

| Поле | Что значит |
| --- | --- |
| `ts_wall` | wall-clock, мс (может прыгать при переводе часов) |
| `ts_mono` | время от старта процесса, мс (сравнимо только внутри процесса) |
| `session` | случайный id процесса: новый процесс — новая сессия |
| `seq` | порядковый номер события внутри сессии |
| `tag` | канал: `TRACK`, `LIFE`, `PERF`, … |
| `level` | `D`/`I`/`W`/`E` |
| `msg` | событие внутри канала |
| `payload_json` | плоский JSON, без координат и адресов |

Старые поля и их смысл не менялись; `payload` новых событий дополняется
`boot_mono_ms` — см. ниже.

## Канал `LIFE`: абсолютная шкала и причина разрыва

`boot_mono_ms` — `SystemClock.elapsedRealtime()` на момент события. В отличие
от `ts_mono` он не сбрасывается при старте процесса, поэтому сессии можно
упорядочить и измерить время, когда процесса не было:

```
boot_mono_ms - ts_mono = момент старта процесса на шкале загрузки
```

Поле `boot_mono_ms` пишется только в `LIFE`-события (и в `flush`, у которого
есть `since_last_ms`), чтобы не раздувать объём. `ts_mono` в строке остался
прежним — старые парсеры не ломаются.

| Событие | Когда | Ключевые поля payload |
| --- | --- | --- |
| `LIFE/proc_start` | первым событием процесса, до остальных записей | `boot_mono_ms`, `prev_session`, `prev_boot_mono_ms`, `gap_ms` |
| `LIFE/heartbeat` | каждые 5 минут, пока жив процесс | `via` (`thread`/`alarm`), `since_last_heartbeat_ms` |
| `LIFE/freeze_gap` | тик записи или heartbeat увидел паузу ≥ 10 минут | `gap_ms` (фактическая), `source` (`flush`/`heartbeat`) |
| `LIFE/exit_reason` | при старте, по `ApplicationExitInfo` (API 30+) | `reason`, `reason_code`, `age_ms`, `death_wall_ms`, `vendor`, `desc` |

`gap_ms` в `proc_start` — время между последним событием прошлой сессии и
стартом текущей. Метка последнего события хранится в
`filesDir/life-state.txt` (запись tmp+rename, не чаще раза в 60 с), поэтому
переживает убийство процесса: после рестарта разрыв равен времени отсутствия,
а не нулю.

Причина смерти не теряется, даже если код незнаком: `reason_code` пишется
всегда, а вендорский тег вытаскивается из текста описания
(`iAwareF[Thermal]` у Huawei). `reason=exit_self` — штатный выход, проблемой
не считается.

Тишина Fused (`TRACK/no_fix`) считается от последнего **подтвержденного**
flush-тика, а не от пустоты буфера: пачка фиксов, накопившаяся за время
заморозки, больше не маскирует дыру. Порог — 5 минут
(`SilenceGap.THRESHOLD_MS`).

## Разбор: `scripts/analyze-devlog.py`

Только стандартная библиотека, сеть не нужна:

```
py -3 scripts/analyze-devlog.py <файл.jsonl | папка> [...]
```

Можно передать несколько файлов или папку — скрипт сам найдёт `fog-*.jsonl`.
Порог печатаемых разрывов меняется флагом `--gap-min` (по умолчанию 5 минут,
как у `no_fix`).

Что печатает:

- **сессии процесса** — границы по wall-clock, `boot_anchor`, `proc_start` с
  разрывом и прошлой сессией, причину прошлой смерти;
- **разрывы** — между сессиями (процесс отсутствовал) и внутри сессии
  (заморозка / цикл записи стоял / причина неизвестна);
- **ритм каналов** — watchdog, heartbeat, flush: медиана и максимум;
- **тишину Fused** — каждый `no_fix` с фактической длительностью;
- **дни** — принятые точки и `day_stats`, плюс дни без записи (нет файла или
  нет принятых точек);
- **шум** — доля `TRACK/day_branches` в объёме каждого файла.

Порядок сессий: по абсолютной шкале `boot_mono_ms`, если она не противоречит
wall-clock. При перезагрузке (шкала сбрасывается) или переводе часов скрипт
честно пишет, что порядок по wall-clock, — догадок не делает.

### Пример

```
== Разрывы ==
  2026-10-21 16:58:23 -> 2026-10-21 20:44:52  (226 мин)  session 0ed4a2ce
      причина неизвестна (лог до канала LIFE)
```

Так выглядит полевая дыра 21.10 в логе **старой** версии: канала `LIFE` там
ещё нет, поэтому причина не выдумывается. После установки сборки с этим
change на месте такой строки будет `заморозка процесса` или
`процесс отсутствовал … причина: low_memory` — с фактической длительностью.

### Проверка шума

`TRACK/day_branches` пишется только когда счётчики дня изменились. На логе
21.10 до правки доля была 703/1205 = 58.3 % (скрипт помечает `ШУМНО`), цель —
не больше 20 % (`scripts/analyze-devlog.py` печатает вердикт по каждому
файлу). Пустые тики больше не создают строк, при этом `counters.json`
по-прежнему материализует нули.

## Старые логи

Логи до этой версии не содержат `LIFE`: разрывы в них видны, но причина
помечается `причина неизвестна (лог до канала LIFE)`. Это ожидаемо и не
является ошибкой скрипта — для атрибуции нужен лог, снятый на сборке с
каналом `LIFE`.
