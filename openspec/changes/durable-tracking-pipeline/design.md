# Design

## Context

Сейчас фиксы приходят колбэком `requestLocationUpdates(request, callback, Looper.getMainLooper())` внутрь процесса, а весь конвейер (доверие, буфер, кэш `trackId`, граница суток) живёт в памяти сервиса. Мотивация — `proposal.md`; требования — `specs/fix-journal`, `specs/day-ledger`, `specs/tracking`.

Ограничения, которые формируют подход:
- Android 12+ запрещает свободный старт foreground-сервиса из фона, поэтому ресивер не может «поднять сервис и всё сделать сразу».
- Huawei замораживает процесс целиком вместе с heartbeat даже при удержанном wake-lock (`TRACK/wakelock held=true` и паузы 185–720 с на профиле ACTIVE в разборе 08.11).
- БД уже содержит `raw_fixes`, `track_points`, `visited_cells`, `counters`; миграция должна быть дешёвой и обратимой на устройстве.

## Goals / Non-Goals

**Goals:**
- Ни один доставленный фикс не теряется и не дублируется, даже если процесс убит сразу после доставки.
- Обработка воспроизводима: повторный проход по журналу даёт те же точки, тот же туман и те же счётчики.
- Привязка «день → строка трека» перестаёт быть эвристикой.
- Расхождения дня видны и ремонтируются без выгрузки.

**Non-Goals:**
- Ускорение холодного старта карты и кэш тайлов (отдельный change).
- Изменение правил доверия `TrustEngine` и порогов фильтра.
- Переход на другого провайдера локации или собственный fused-сервис.

## Decisions

### D1. Подписка на локацию через PendingIntent, а не через колбэк

`LocationServices.getFusedLocationProviderClient(context).requestLocationUpdates(request, pendingIntent)` с `PendingIntent.getBroadcast` в `LocationFixReceiver`, объявленный в манифесте с `android:exported="false"`. Платформа сама поднимает процесс на каждый broadcast и держит на это время wakelock.

Альтернативы: (а) оставить колбэк и добавить wake-lock — уже провалилось в 1.9.0; (б) отдельный foreground-сервис с `setForegroundServiceType(location)` — Huawei всё равно морозит; (в) `AlarmManager` каждую минуту — батарея и те же ограничения OEM.

### D2. Ресивер только пишет, обработка — по триггеру

Ресивер выполняет один `INSERT OR IGNORE` в `fix_inbox` и возвращается; сервис не стартует. Обработку запускают: активный сервис (если он уже работает — его flush-цикл), `OneTimeWorkRequest` с уникальным именем из ресивера, watchdog-канал и открытие приложения.

Альтернатива — старт FGS прямо из ресивера — отпадает из-за ограничения фонового старта на Android 12+.

Следствие: данные гарантированно целы, но точка может появиться в треке с задержкой до следующего триггера. Это осознанный размен: полнота важнее секундной свежести.

### D3. Журнал фиксов с естественным ключом дедупликации

```
fix_inbox(
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  key TEXT NOT NULL UNIQUE,      -- fix_time|lat|lon
  fix_time INTEGER NOT NULL,
  recv_ms INTEGER NOT NULL,
  lat REAL NOT NULL, lon REAL NOT NULL,
  acc REAL NOT NULL, speed REAL,
  source TEXT NOT NULL,
  day TEXT NOT NULL,             -- локальная дата метки, считается при приёме
  state INTEGER NOT NULL DEFAULT 0,  -- 0 новый, 1 обработан, 2 дубликат/мусор
  error TEXT
)
CREATE UNIQUE INDEX fix_inbox_key ON fix_inbox(key);
CREATE INDEX fix_inbox_pending ON fix_inbox(state, fix_time);
```

`day` вычисляется один раз при приёме — это единственное место, где календарь точки определяется, дальше он не пересчитывается.

Альтернатива: хранить только сырые фиксы без ключа и дедуплицировать на обработке — дороже и не даёт защиты от повторной доставки на входе.

### D4. Консьюмер восстанавливает контекст из БД, а не из памяти

Окно доверия — 60 с (`TrustEngine.HISTORY_MAX_AGE_MS`). Значит для продолжения достаточно поднять из `track_points` хвост текущего дня длиной в это окно при старте обработки, а `PrevState` восстановить из последней точки (её `state`, `trust`, координаты как якорь). Никакого JSON-состояния в БД не нужно.

Пачка обрабатывается кусками по 200 строк: транзакция на кусок, «точки + туман + счётчики + state=1» атомарно. Смерть посреди куска — кусок откатывается целиком, строки остаются `state=0`.

```
flushInbox():
  rows = SELECT * FROM fix_inbox WHERE state=0 ORDER BY fix_time, id LIMIT 200
  if rows.empty: report(idle) ; return
  ctx = restoreContext(rows.first().day)     // хвост точек + PrevState
  verdicts = rows.map { TrustEngine.evaluate(...) }   // чисто, без БД
  withTransaction {
     points = insertPoints(verdicts)
     openFog/confirmPending
     counters += ...
     UPDATE fix_inbox SET state=1 WHERE id IN rows.id
  }
```

### D5. Реестр дней вместо `latestInRange`

```
days(day TEXT PRIMARY KEY, track_id INTEGER NOT NULL, opened_at INTEGER NOT NULL)
```

`openDay(day)` внутри той же транзакции, что и запись точек: `SELECT` → нет строки → `INSERT` трека + `INSERT` дня. `trackId` не кэшируется в сервисе как источник истины: источник — таблица, кэш только ускоряет.

Миграция: `INSERT INTO days(day, track_id, opened_at) SELECT day, id, startedAt FROM (SELECT id, startedAt, localdate(startedAt) day, ROW_NUMBER() OVER (PARTITION BY localdate(startedAt) ORDER BY startedAt DESC) rn FROM tracks) WHERE rn=1`. `localdate` считается в Kotlin при бэкфилле, чтобы не зависеть от SQLite-таймзоны.

### D6. Аудит дня — пересчёт, а не эвристика

`DayAudit.recompute(points)` — чистая функция: `pointsCount` = число строк, `time_s` = `TrackChunking.totalSpanMs` по MOVING, `distanceM` = сумма по соседним MOVING-точкам с `trust >= TRUST_OPEN` (те же правила, что `batchDistance`). Аудит сверяет значения строки и счётчиков с пересчётом и при расхождении перезаписывает их через `counterDao.set` (абсолютные значения, не инкременты).

Чужие точки (метка не того дня) переносятся в строку своей даты, после чего оба затронутых дня пересчитываются аудитом.

Альтернатива — «мягкий» отчёт без ремонта — оставлена как первый шаг: сначала событие, ремонт включает флагом, чтобы не портить данные в поле.

### D7. Память перестаёт быть точкой потери

`flushLocked`: буферы очищаются только после успешного коммита; при исключении содержимое возвращается в начало очереди; `CancellationException` пробрасывается, а не глотается `runCatching`. Счётчики (eco/rejected/branches) снимаются в снимок до записи и возвращаются при отказе — расхождение вида `rejected=238 при eco_fix=59` становится невозможным.

### D8. Проверка на стенде, а не в поле

`InboxReplay` в JVM-тестах: лента событий (`fix`, `kill`, `rollover`, `duplicate`) прогоняется через консьюмер с фейковым DAO; инварианты — те же, что у аудита. Instrumented-сценарии на эмуляторе: `am kill`, `cmd deviceidle force-idle`, двойная доставка, полночь с очередью.

## Migration Plan

1. Room v1→v2: создать `fix_inbox` и `days`, бэкфилл `days` из `tracks` (одна строка на дату, новейшая по `startedAt`).
2. Откат: приложение 1.9.0 продолжает работать на v1, потому что старые таблицы не меняются; новая версия читает `tracks` как раньше. Понижение версии БД — только переустановкой.
3. Первый запуск новой версии: `prioritize` — обработать остаток журнала (он пуст), затем обычный цикл.

## Risks / Trade-offs

- **ОС подавляет broadcast от Fused на Huawei** → ресивер не сработает вообще. Смягчение: watchdog-канал и срабатывание при открытии приложения; событие `TRACK/inbox_idle` с числом ожидающих покажет это в логе.
- **Задержка появления точки в UI** → обработка при открытии приложения и при любом тике живого сервиса; карточка дня показывает «ожидает обработки N фиксов».
- **Миграция на живых данных** → миграция только добавляет таблицы; бэкфилл идемпотентен и пересчитывается при аудите.
- **Обработка конкурирует с живым сервисом** → все записи идут через транзакции, `state=1` ставится в той же транзакции; повторный проход берёт только `state=0`.
- **Двойная подписка (старая и новая) даст дубли** → старую колбэк-подписку убрать в том же коммите; дубли всё равно отсекаются ключом.

## Open Questions

- Достаточно ли `OneTimeWorkRequest` из ресивера на этом устройстве, или нужен дополнительный точный будильник каждые 2–3 минуты в движении? Решается полевым замером после первой сборки.
