# Design

## Context

Сейчас темп записи решают три места: `EcoGovernor` (интервалы), `TrustEngine` (вердикт движения) и `TrackingWake` (удержание CPU). Мотивация — `proposal.md`; требования — `specs/motion-state` и `specs/battery-eco`.

Полевой прогон 09.11 дал замеры: за сутки 8 `freeze_gap` (2,3 ч), потери движения — два отрезка по ~4 минуты (14:06 и 14:48), задержка старта поездки 2–3 минуты. Ложный выброс 9,25 км доверие поймало само (fog=2), трогать его не нужно.

## Goals / Non-Goals

**Goals:**
- Сократить задержку старта движения до секунды-десятков секунд.
- Убрать рассинхрон «профиль STANDBY, вердикт MOVING».
- Получить измеряемую метрику задержки, пригодную для A/B.

**Non-Goals:**
- Борьба с OEM-фризером (это настройки устройства, evidence уже есть).
- Пересчёт дистанции и джиттера.
- Изменение ворот тумана и `TrustEngine`.

## Decisions

### D1. Единый `MotionState` вместо трёх источников правды

`MotionState: STILL | MOVING | UNKNOWN`, переходы по фиксу (скорость, точность, зазор), по переходу активности и по тишине. Эко-профиль, интервал и wake-lock выводятся из состояния одной функцией `planFor(state)`.

Альтернатива — оставить как есть и подкрутить пороги: лечит симптом, рассинхрон остаётся.

### D2. Activity Recognition через PendingIntent, а не колбэк

`requestActivityTransitionUpdates` с `PendingIntent` в `ActivityTransitionReceiver` (manifest, `exported=false`). Переходы STILL→WALKING/IN_VEHICLE будят процесс так же, как Fused-broadcast. Колбэк отброшен: он живёт в процессе и умирает вместе с ним.

Нужен `com.google.android.gms.permission.ACTIVITY_RECOGNITION` и runtime `ACTIVITY_RECOGNITION` на API 29+. Без GMS — деградация к GPS и событие `TRACK/wake_source_unavailable`.

### D3. Быстрый путь по первому фиксу

Условие: `gap > 2 × interval`, `acc ≤ 25 м`, `speed ≥ 1 м/с`, фикс не мок. Тогда `UNKNOWN/STILL → MOVING` сразу. В поле именно эта ветка съедала 2–3 фикса: первый после тишины уходил в SUSPECT, и только третий подтверждал движение.

Альтернатива — снизить `SILENCE_RESET_S`: ломает защиту от выбросов после пауз, отвергнуто.

### D4. STANDBY расслабляется только при доступном AR

60 с по умолчанию; 120–180 с, только если переходы активности реально доставляются. Без AR не расслаблять — поездка начнётся с дырой.

### D5. Метрика задержки — `idle_ms`

Уже пишется в `TRACK/eco_state` при уходе из STANDBY (зазор до предыдущего фикса). Бюджет: медиана ≤ 60 с, хвост ≤ 3 мин. Отдельный счётчик не заводим — считается разбором дня.

## Risks / Trade-offs

- **Huawei подавляет и AR-переходы** → остаются GPS и fast-path; `idle_ms` покажет, что AR не помог.
- **Ложные переходы** (телефон в руке) → лишний расход, но туман открывает всё равно вердикт.
- **Нет разрешения ACTIVITY_RECOGNITION** → запись работает на GPS, в лог пишется причина.
- **Состояние не персистится** → после рестарта `UNKNOWN`, восстановление из последнего фикса.

## Open Questions

- Достаточно ли STILL→WALKING/IN_VEHICLE или нужны RUNNING/ON_BICYCLE — после первого дня замеров.
