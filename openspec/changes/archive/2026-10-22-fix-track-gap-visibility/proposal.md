# Proposal

## Why

Записи трека теряются, и владелец не может понять почему. Полевой разбор 19–22.10 на Huawei P60 Pro вскрыл три разных механизма потерь, и все три сейчас невидимы:

1. **OEM убивает пакет** (`iAwareF[Thermal]`, `exit-info` 19.10 04:34). Будильник `AlarmManager` внутри пакета снимается системой, `WorkManager`-job отменяется — watchdog не может вызвать сам себя. 20.10: **ноль счётчиков за день, даже `tracks_day` отсутствует**, лог-файл не создан. Пакет ожил только 21.10 09:18, когда владелец открыл приложение руками.
2. **OEM замораживает процесс** (21.10 16:58→20:44, 226 мин). Процесс жив (`seq` без разрыва, тот же pid), но заморожен: flush-цикл не тикает, WorkManager и AlarmManager молчат одновременно. `setAndAllowWhileIdle` будит **устройство**, но не размораживает **процесс**. Проснуться может только внешнее событие (тут — GPS-фикс).
3. **Точки забраковываются вердиктом** (21.10: 164 из 372 принятых точек с `fogOpened=2` — туман не открыт никогда).

Следствия, которые делают потерю недиагностируемой:

- **Лог молчит ровно тогда, когда всё сломалось.** Все следы (`start_attempt`, `watchdog`, `no_fix`) лежат внутри пакета, который убивают. Счётчик `no_fix` за 21.10 показал **одну** запись при дыре в 226 минут, потому что `flushIfStarved()` вызывается из `flush()`, а flush в дыре не тикает — счётчик не видит собственную смерть.
- **Метрика времени дня раздута.** `time_s` считается как `moving.last().time − moving.first().time` по всему батчу без реза по времени: 21.10 — 1574 с из 3678 с это разрывы между MOVING-точками, а не движение; 10.04 — `time_s=18647` при `dist=325 м`.
- **Пользователю некуда идти за «починить».** Он не знает, что такое `iAwareF[Thermal]`. Инструкция в онбординге («отключите оптимизацию батареи и разрешите автозапуск») — это текст, который игнорируют.

## What Changes

- **Наблюдаемость разрывов, переживающая заморозку.** Новый тег `LIFE` с событиями `proc_start` (с разрывом с прошлой сессией), `heartbeat` (раз в 5 мин из alarm-канала), `freeze_gap`, `exit_reason` (причина смерти процесса из `ApplicationExitInfo`). Плюс: `no_fix` начинает считать разрыв по времени последнего тика, а не по пустому буферу.
- **Честная метрика времени дня.** `time_s` режется по максимальному спану так же, как при импорте (`REBUILD_SPAN_MS`), — в живом пути записи.
- **Разгрузка и структурирование логов.** `day_branches` пишется только при изменении счётчиков (шум ↓ ~80 %); `flush` получает `since_last_ms` и `since_boot_ms`; `PERF/stall` отделяется от `PERF/jank`; событие `TRACK/day_stats` пишет дневные счётчики в лог, чтобы «какие дни пустые» читались из одного файла.
- **Скрипт анализа** `scripts/analyze-devlog.py`: одна команда выдаёт сессии, разрывы, ритм watchdog, пустые дни.
- **Кнопка «Проверить фоновую запись» в Настройках.** Приложение **измеряет** своё состояние (`areNotificationsEnabled`, `isIgnoringBatteryOptimizations`, `ApplicationExitInfo`, возраст последней точки) и показывает конкретный сломанный пункт с кнопкой перехода в нужный экран настроек — без инструкций для пользователя.
- **Запрос разрешения на уведомления.** На устройстве владельца `POST_NOTIFICATIONS` не выдан, поэтому FGS-уведомление невидимо — для OEM это сигнал «приложение фонов��е, его можно душить».

### Modified Capabilities
- `tracking-reliability`: наблюдаемость разрывов, переживающая заморозку и убийство пакета; честная фиксация того, что watchdog не может пережить убийство пакета.
- `dev-logging`: структура и шум лога, `LIFE`-канал, раздельная диагностика `stall`/`jank`, дневные счётчики в логе.
- `tracking`: корректная метрика времени дня (`time_s` режется по спану).
- `app-shell`: экран проверки фоновой записи в Настройках с переходами в настройки системы.

## Impact

- **Код:** `tracking/TrackingService.kt` (flush-цикл, `flushIfStarved`, `no_fix`), `tracking/TrackingWatchdog.kt` + новый `tracking/TrackingLife.kt` (LIFE-канал, heartbeat), `diag/DevLog.kt` (новые события, `day_branches` по изменению), `diag/DevDiagAggregators.kt` (`PERF/stall`), `data/FogRepository.kt` (`time_s` по спанам), `ui/screens/SettingsScreen.kt` + новый экран проверки фоновой записи, `ui/screens/OnboardingScreen.kt` (запрос уведомлений), `scripts/analyze-devlog.py` (новый).
- **Спеки:** `tracking-reliability`, `dev-logging`, `tracking`, `app-shell` — дельты.
- **Устройство:** Huawei P60 Pro (MNA-LX9), Android/HarmonyOS, targetSdk 36. Проверено на устройстве: `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` резолвится **только с `data=package:`**; `com.huawei.systemmanager/.startupmgr.ui.StartupNormalAppListActivity` и `.../.appcontrol.activity.StartupAppControlActivity` резолвятся; `ApplicationExitInfo` доступен (API 30+); `POST_NOTIFICATIONS` сейчас `granted=false`.
- **Обратная совместимость:** формат строки лога не меняется; добавление полей в payload — additive. `time_s` в счётчиках станет меньше для дней с разрывами (это исправление, но цифра за прошлые дни в уже собранных `counters.json` останется прежней).
- **Риск:** запрос `POST_NOTIFICATIONS` на онбординге добавляет шаг; `ApplicationExitInfo` требует API 30+ (minSdk 26 — нужен fallback).
