# fix-stale-batch-day

Разбор полевой выгрузки `track-debug_2026-11-08_2026-11-08` с P60 Pro (08.11, сборка 1.9.0.79).

Что показал разбор:
- в 01:39:18 `TRACK/day_stats via=date_change` переключил день на 08.11, следом `TRACK/flush batch=90` отдал пачку, накопленную за 9 часов заморозки (`freeze_gap` 32 455 560 мс, `since_last_ms` 32 457 132);
- 89 из этих точек — вечер 07.11 (17:00–20:10, id 48617–48705), и все они легли в трек 89, то есть в строку 08.11 (`TRACK/day_chunk track_id=89` после рестарта в 13:26, `tracks_day_2026-11-08=1`);
- вечер 07.11 в своей строке остался дырой: `day_stats` закрыл 07.11 на 376 точках и 50,7 км ещё до этой пачки, а дистанция и время пачки ушли в счётчики 08.11.

Изменения:
1. **Резчик батча по суткам** (`FogRepository.groupByDay`): чистая функция, группы по возрастанию даты, внутри — порядок прихода; дата считается по метке точки в зоне устройства.
2. **Запись по строкам дней** (`TrackingService.flushLocked`): каждая группа пишется в свою строку (`openDayChunk(day)` для прошлых суток, кэш `trackId` — только для текущих), `appendPoints(..., date = day)` — дистанция, время и площадь идут в счётчики своей даты; якорь пробуждения и метрики префикса — только новейшей группе.

Решение владельца 2026-11-08: правка идёт отдельным change, `proposal.md` и
`design.md` не заводить — выгрузка, причина и объём изменений описаны здесь.

Не входит (отдельные задачи): причины заморозки процесса (12 `LIFE/freeze_gap` на 24,5 ч за сутки), прямая нить через дыру 9,7 мин и 3,66 км, длительность дня в карточке истории.
