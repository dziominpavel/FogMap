## Context

Текущая архитектура: `FogRepository.appendPoints` открывает ячейки и инкрементирует глобальные counters (`area_cells_*`) в одной Room-транзакции. Ячейки хранятся в `visited_cells` с PK (x,y,z), пирамида z21–z14, веса через `FogGrid.weightOf`. Географических регионов сейчас нет. Мотивация — proposal.md.

## Goals / Non-Goals

**Goals:**
- 13 регионов Беларуси с полигонными границами (OSM)
- Materialized counters `region_<id>_cells` в существующей транзакции
- Экран прогресса: км² + % для каждого региона

**Non-Goals:**
- Полигонная отрисовка границ на карте (только метрики)
- Иерархия регионов (плоский список с полем type)
- Ачивки и социальные функции (отдельные changes)
- Экспорт/импорт региональных counters

## Decisions

**1. Полигон вместо bbox**
- Решение: каждый регион — полигон (список вершин) из OSM GeoJSON.
- Альтернатива: bbox (4 точки) — отклонена, погрешность по углам неприемлема для городов.
- Алгоритм: ray casting point-in-polygon.

**2. Хранение регионов: Kotlin constants vs Room table vs assets**
- Решение: Kotlin constants в `region/Regions.kt` (или объекте).
- Альтернатива A: Room table — избыточно, данные статичны.
- Альтернатива B: assets/GeoJSON — парсинг при старте, лишняя сложность.
- Обоснование: 13 регионов × ~100-500 точек — помещаются в код, компилируется.

**3. Инкремент в существующей транзакции**
- Решение: в `FogRepository.appendPoints` после `openBaseCells`/`filterCovered` проверять каждую новую ячейку на принадлежность полигонам и инкрементировать `region_<id>_cells`.
- Альтернатива: отдельная фоновая задача — добавляет задержку, сложность синхронизации.

**4. Denominator: totalAreaKm2 из OSM vs вычисление**
- Решение: хардкод `totalAreaKm2` в константах (из данных OSM/Wikipedia).
- Альтернатива: вычислять площадь полигона — нужно для verification, но не в runtime.

**5. UI: отдельный экран vs секция в Stats**
- Решение: отдельный экран `RegionProgressScreen`, доступный из Stats (кнопка/вкладка).
- Обоснование: 13 карточек сгруппированы по типу — тесно в существующем Stats.

## Risks / Trade-offs

- [Точность полигонов OSM] → Использовать admin_level=4/6 boundaries, проверить на Минске.
- [Производительность point-in-polygon на каждой ячейке] → bbox pre-filter перед ray casting; 13 регионов — приемлемо.
- [Рост числа регионов] → Дизайн плоский, добавление = новая константа.
- [Разные версии OSM данных] → Зафиксировать дату/снимок данных в комментарии.

## Migration Plan

1. Добавить `region/Regions.kt` с константами.
2. Расширить ключи counters (новый префикс `region_`).
3. Миграция БД не требуется (counters — существующая таблица).
4. Rollback: revert кода, counters остаются безвредными.
