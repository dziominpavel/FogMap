## Context

`DevLogFile` (`app/src/main/java/ru/fogmap/diag/DevLogFile.kt`) — фоновый writer: очередь на 4096 строк → один поток, append в `cacheDir/logs/fog-YYYYMMDD.jsonl`, лимит 2 МБ на файл дня с маркером `log_rotated`, чистка `cleanupOlderThan24h()` по константе `TTL_MS = 24 ч`, вызывается из `FogMapApp.onCreate` в `appScope.launch` (не блокирует старт). TTL 24 ч зафиксирован и в спеке `dev-logging` («Фоновый трек-лог и хранение с TTL»). Полевой разбор 2026-10-11 показал: вчерашний `fog-2026-10-10.jsonl` уничтожен TTL, поэтому разбор дыр 10.10 невозможен — прямая причина «вообще нет данных». Мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**

- Диагностический лог переживает минимум неделю: лог вчерашнего/позавчерашнего дня доступен для шаринга с экрана «Диагностика» без правки кода.
- Сохранить прежние гарантии: лимит 2 МБ на файл дня, чистка в фоне при старте, без блокировки старта процесса, без изменений формата и приватности.

**Non-Goals:**

- Менять формат строк, состав событий, приватность (координаты в лог не пишутся — остаётся).
- Переносить логи в постоянное хранилище (`filesDir`), делать фоновое копирование/бэкап или автозагрузку наружу.
- Чистку по календарю/воркеру — чистка остаётся событийной (при старте приложения).
- Решать проблему дыр в записи трека (doze/Huawei, watchdog) — это отдельный скоуп `tracking-reliability`.

## Decisions

1. **TTL = 7 дней (168 ч), константа `TTL_MS`.** Альтернативы: 48 ч — мало для полевого цикла «поездка в выходные → разбор в середине недели»; 30 дней — `cacheDir` объективно временный (система может чистить), объём вырос бы до ~60 МБ.
2. **Чистка остаётся при старте приложения в фоне** (`appScope.launch`), как сейчас. Альтернатива — периодический воркер: избыточен, чистка дёшева, а события старта и так часты (по логу 11.10 процесс стартует ежедневно).
3. **Имя метода `cleanupOlderThan24h` → `cleanupExpired`.** Альтернатива — оставить имя (минимум правок): отвергнута, имя привязано к конкретным суткам и соврёт при следующей смене TTL.
4. **Суммарный лимит не добавляем.** Граница объёма уже есть: ≤2 МБ на файл дня × 7 дней ≈ 14 МБ в `cacheDir`; фиксированное число дней делает отдельный суммарный счётчик избыточным. Кнопка «Очистить логи» остаётся ручным сбросом.
5. **Граница TTL покрывается юнит-тестом через чистую функцию** (`isExpired(lastModifiedMs, nowMs)` в companion): предсказуемо тестируема без Android Context. Альтернатива — Robolectric-тест `DevLogFile` с реальной файловой системой: в проекте нет этой зависимости, ради одной константы её не добавляем.

## Risks / Trade-offs

- [Рост `cacheDir` с ~2 МБ до ~14 МБ] → принимается: временные данные, система вправе чистить `cacheDir`, лимит на файл дня сохранён, есть ручная очистка.
- [Диагностические логи живут дольше] → приватность не меняется (координат в лог нет по построению), файлы не покидают устройство без явного шаринга владельцем.
- [Код и основная спека расходятся до архивации change] → осознанно: спека синхронизируется при `openspec archive`; change не архивируется до выпуска APK.

## Migration Plan

- Изменение обратимо: откат = вернуть `TTL_MS` 24 ч, при следующем старте излишки удалятся (уже удалённые файлы не воскресают — полевой разбор ведётся из `dist/`).
- Полевой контроль после установки: на «Диагностике» в списке файлов видны логи за прошлые дни, после перезапуска приложения «старше недели» удаляются.
