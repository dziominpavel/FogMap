# Design — fix-pending-gate-false-vetoes

## Context

Мотивация и доказательства — в `proposal.md` (Why). Здесь — только технический контекст:

- `PendingGate.adjudicate(pendingAsc, anchor, newest)` — чистая функция без состояния; ворота C подтверждают точки после `LAG=2` successors, `roundTrip`-вето ловит короткие круговые вылеты, `stale`-вето (`MAX_PENDING_AGE_S=600`) — только не-MOVING.
- `FogRepository.confirmPending` читает хвост запросом `unopenedTail(trackId, TAIL_LIMIT=32)` (`ORDER BY time DESC LIMIT 32`), якорь — `lastOpenedPoint` (`fogOpened=1`, новейший), `newest = batch.last()`.
- `openBaseCells(points, prev)` рисует кисть каждой точки, коридоры между последовательными парами и линк `prev`→первая точка без проверки времени.
- Хвост в БД после вставки батча = старые pending + свежие точки, наружу по времени.
- Реплей на данных 25.09 (`replay_gate.py`) воспроизводит 49/49 ложных `veto_return` и 2 вечные LAG-точки при 0 расхождений — отладочная установка закончена, код менять можно.

## Goals / Non-Goals

**Goals:**
- Ложный `veto_return` невозможен в принципе: геометрия «туда-обратно» проверяется только во временно-монотонной последовательности.
- Никакое число точек в батче не может осиротить pending: окно хвоста не ограничено фиксированным числом.
- Ничто не висит вечно: LAG-хвост дренируется по wall-clock, прошлые дни долечивает разовый проход восстановления.
- Сшивка коридора не рисует прямые через непосещенную местность при инверсии времени.
- Валидация на реальных данных 25.09: 0 `veto_return`, все 51 точка подтверждена.

**Non-Goals:**
- Не разбираемся, почему FGS был заморожен 6–8 минут (OEM battery/Doze Huawei) — конвейер обязан переживать любую морозку, а не предотвращать ее.
- Не трогаем TrustEngine, пороги ворот A/B, FLUSH_SIZE/FLUSH_INTERVAL_MS (постоянные верны, голодание flush — следствие морозки, а не констант).
- Не чиним «шторм камеры» при открытии карты (вторичный дефект, отдельный разбор).
- Не переписываем историю честных вето.

## Decisions

### D1. Временная монотонность roundTrip (фикс A)

`roundTrip` требует `anch != null && c.time > anch.time && out > VETO_MIN_DIST_M && back < RETURN_RATIO * out`. Якорь продвигается только вперед: `anch = c` только при `c.time > anch.time`, иначе остается прежним.

*Альтернативы:* (а) оставить как есть и ловить инверсию в `confirmPending` — геометрическое правило живет в двух местах, легко сломать; (б) сортировать хвост и обрезать старые точки до якоря — теряет точки молча. Выбрана проверка в точке принятия решения: правило и его тест живут рядом в `PendingGate`.

*Оговорка (см. Risks):* в редком случае инверсии подтвержденная точка открывается кистью без линка к якорю — приемлемо, потому что нормальный поток (все кандидаты новее якоря) обрабатывается штатно и вето честных круговых вылетов сохраняется.

### D2. Окно хвоста без лимита (фикс B)

`unopenedTail` теряет `LIMIT :limit` — `SELECT ... WHERE fogOpened = 0 ORDER BY time DESC`, разворот в asc на месте. Обоснование безопасности: в установившемся состоянии неоткрытых ровно `LAG` (+ единичные осиротевшие), потому что каждый flush закрывает (`1`) или ветует (`2`) весь хвост; снятие лимита не раздувает чтение. При морозке хвост = батч любого размера, и это ровно тот случай, который нужно увидеть целиком.

*Альтернатива:* поднять лимит до сотен — любой порог повторяет класс бага «хвост старше лимита не виден». Лимит убирается полностью.

### D3. Линк только при порядке времени (фикс C)

В `confirmPending` линк `anchorRaw`→первая подтвержденная рисуется только если `первая.time > anchorRaw.time`. Коридоры между последовательными парами подтвержденных точек не трогаются (они и так asc по времени).

*Альтернатива:* всегда гнать линк — при инверсии дает прямую 2–3 км через непосещенную территорию (наблюдаемый дефект).

### D4. Дренаж LAG по wall-clock (фикс D)

В `adjudicate` в `actionable` входят: как раньше `pendingAsc.dropLast(LAG)`, плюс любые точки с `(newest.time - c.time)/1000 > MAX_PENDING_AGE_S` (включая последние LAG позиции). Протухание уже не-MOVING не касается — старые точки движения подтверждаются, старые статики честно получают `veto_stale`.

*Альтернатива:* дренаж только в `confirmPending` — дублирует правило вне чистой функции и не покрывается её тестами.

### D5. Восстановление 25.09 — разовый проход при старте, без версии БД (фикс E)

Схема не меняется (новых колонок нет), поэтому `version = 7` остается. Восстановление — функция `FogRepository`, запускаемая один раз при старте приложения, с флагом-маркером в `counters` (`pending_gate_repair_v1`), который пишется ПОСЛЕ успешного прохода. Проход идемпотентен: повторный запуск без флага находит те же строки и дает тот же результат.

Алгоритм:
1. Найти треки с точками `fogOpened=2 AND rejectReason='veto_return'` и/или застрявшими `fogOpened=0` старше `MAX_PENDING_AGE_S` относительно новейшей точки трека.
2. Для каждого трека — чистая функция `FogRepository.planRepair(points)` (комpanion, unit-тесты `RepairPlanTest`): кандидаты asc, на каждого кандидата своя контекстная пара — **якорь** = самая новая открытая точка строго старше кандидата (включая открытые в этом же проходе), **`newest`** = первая точка трека ПОСЛЕ кандидата («куда пошла траектория», аналог `batch.last()` живого flush; конец трека → сам кандидат, тогда `out == back` и вето геометрически невозможно). Предикаты — те же, что в `PendingGate.adjudicate` (временная монотонность roundTrip D1, протухание только не-MOVING).
   *Почему не один `anchor=lastOpenedPoint`/`newest=новейшая точка` на трек (первоначальная формулировка):* честный вылет старше новейшего открытого якоря — инверсия D1 блокирует roundTrip и точка подтверждается (честное вето переоткрылось бы); а обратный вариант с `back` до новейшей точки трека воспроизводит исходную геометрию ложного вето (дом→маршрут→дом). Контекст «открытый якорь до + продолжение траектории после» различает оба случая: честный вылет возвращается в якорь уже в следующей точке, ложный — продолжает маршрут.
3. Подтвержденные: `openBaseCells(confirmed, anchor)` с линком только при порядке времени → `filterCovered` → `insertChunked` → `promoteCascade` → `markReopened` (снимает вето вместе с его причиной), инкремент `area_cells_*` по дню трека и региональных счетчиков.
4. Повторно ветованные: `markClosedWithReason` с той же причиной (честные вето остаются нетронутыми — исправленная логика на корректной последовательности воспроизводит их же вердикт).
5. Записать флаг.

*Почему не Room-миграция v7→v8:* SQL не умеет haversine/кисти/коридоров — миграция могла бы только пометить строки, а кто-то должен был бы открыть клетки. Реальный ремонт — та же Kotlin-логика, что и живой flush; прятать ее в миграцию значит не иметь на нее unit-тестов. *Почему не полный rebuild из raw (track-debug):* требует ручного экспорта/импорта владельцем — восстановление должно произойти само.

### D6. Валидация реплеем до и после

`replay_gate.py` (temp) расширяется: прогон исправленной логики на `tracks/2026-09-25.jsonl` + flush-события. Критерий: 0 `veto_return`, 51/51 точка подтверждена, честные вето на контрольных данных (другие дни с `veto_return`) остаются ветованными. Скрипт — временный, в репозиторий не коммитится; воспроизводимость гарантируется через unit-тесты `PendingGateTest`.

## Risks / Trade-offs

- [В редком случае инверсии подтвержденная точка-«орфан» открывается без линка к якорю — возможен отдельный островок тумана] → Сшивка между последовательными парами точек сохраняется, а соседние flush обычно дают связную нить; из двух зол выбран островок вместо прямой сквозь город и вместо потери маршрута.
- [Снятие LIMIT читает хвост целиком — в теории большой memory-list при аномальном накоплении] → Состояние между flush ограничено батчем морозки (десятки-сотни точек, строки легкие); альтернатива — эвристика, повторяющая баг.
- [Ремонт открывает клетки постфактум — единократный всплеск площади в счетчиках] → Ожидаемо и честно (клетки действительно посещены); сценарий спеки явно это декларирует.
- [Флаг ремонта в `counters` можно потерять при сбросе прогресса] → Сброс прогресса и так удаляет туман — ремонтировать нечего; повторный ремонт в этом случае идемпотентен и безопасен.
- [D4 дренирует старую статику в `veto_stale` позже, чем раньше] → Это уже задекуменное поведение (`veto_stale` только для не-MOVING), меняется лишь момент (раньше точка могла ждать вечно).

## Migration Plan

1. Код A–D + тесты → компиляция, `testDebugUnitTest`, реплей-валидация на 25.09.
2. Ремонт E (одна функция + вызов при старте) → реплей-валидация повторным прогоном.
3. Release через `build-apk.bat release` — версия бампится только там (правила AGENTS.md), в этой сессии `version` не трогаем.
4. Откат: изменения в рабочей копии до коммита; после коммита — revert. Ремонт обратим только полным сбросом прогресса (клетки необратимы по контракту fog-grid) — потому что проход идемпотентен и открывает только доказанно посещенные клетки.
