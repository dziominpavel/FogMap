## Context

См. proposal.md — Why. После change `battery-eco-tracking` (заархивирован 2026-09-20) сервис пишет `mode/profile` в каждый TRACK-лог, считает `eco_fix/stand/gps_ms/flush/prefix` в счетчики БД и семплирует сыряк 1/6 в STANDBY. Ограничения: приватность DevLog (никаких lat/lon), TTL файлов 24 ч, Share отдает один файл за день, поведение трекинга менять нельзя.

## Goals / Non-Goals

**Goals:**
- Один `fog-YYYYMMDD.jsonl` самодостаточен для сверки сна/пробуждений с треком из ZIP.
- Причина каждого wake видна: откуда, насколько далеко от якоря, по какому вердикту.

**Non-Goals:**
- Не меняем профили, пороги, переходы, flush, watchdog, БД, UI.
- Не добавляем новые сигналы (motion, WiFi) — только логируем существующие.
- Не трогаем TTL и Share многих файлов — это отдельный вопрос.

## Decisions

### 1. Обогатить два события, а не плодить новые
`flush` несет эко-снимок пачки (fix/stand/gps_ms — те же числа, что уже сливаются в счетчики), `eco_state` несет причину (from-профиль, wake-м в int, verdict). Новые теги не нужны: парсер уже режет по `|` и читает плоский payload. Альтернатива «отдельное событие eco_stats раз в час» отвергнута: рассинхрон с flush усложняет сверку.

### 2. Дистанция целым числом метров, координат нет
`wake_m` — округленный haversine до якоря на момент перехода (уже считается в `isWakeSignal`). Проверяем через `DevLog.buildPayloadJson`: ключ без `lat/lon` проходит privacy-гейт, значение — число. Альтернатива «писать дельту координат» запрещена приватностью.

### 3. Подавленные дебаунсом переходы не логируем
Штормозащита 10 с остается молчаливой: иначе сонное дрожание заспамит лог. Видим отсутствие перехода по разрыву в `eco_state` + продолжающимся `flush` в старом профиле. Если при полевом разборе окажется слепым пятном — добавим счетчик `eco_debounced` отдельным change.

## Risks / Trade-offs

- [Risk] Payload flush вырастет на 3 числа → Mitigation: числа короткие, flush и так раз в 15 с, лимит 2 МБ/день не трогаем.
- [Risk] wake_m при MOVING-wake без якоря (anchor null) → Mitigation: пишем -1 как «якоря не было», сценарий покрыт.
- [Risk] Старые парсеры JSONL не знают новых ключей → Mitigation: ключи additive, tolerant-парсер их игнорирует.

## Migration Plan

- Одна сборка, откат — предыдущий APK (поведение трекинга идентично, отличаются только логи).
- Валидация: unit-тест payload + ручное чтение JSONL одного дня.
