## Context

См. `proposal.md` (Why) и specs (что). Диагноз 2026-09-23 доказан реплеем: рендер здоров, `LocationFilter` отбросил 47% точек по `acc>25`, `HistPoint` не несёт `speed`, поэтому `TrustEngine` при ходьбе `speed=1.68–2.83` выдавал STAND (143/147), STAND не писался в `track_points` и не открывал туман → 4 `openFog=1`, 213 ячеек. wifi-WAKE срабатывал (`source=wifi`), но `BURST_WINDOW_MS=75с` истекал, а speed-latch `>5 м/с` не переводил пешехода в ACTIVE. Ключевые файлы: `TrustEngine.kt`, `LocationFilter.kt`, `EcoGovernor.kt`, `TrackingService.kt` (HistPoint ~265, запись STAND ~329), `FogRepository.kt`. Ограничения: офлайн-first, без Activity Recognition API, без миграции схемы БД, координат в `DevLog` нет, коммит/пush — только по команде владельца, версия PATCH → 1.5.1 (решение владельца).

## Goals / Non-Goals

**Goals:**
- Ноль STAND при `speed≥1.0 И acc≤25` на реплее 23.09; маршрут/ячейки/дистанция отражают фактическую прогулку (комплексная приёмка: wifi-BURST 180с, Kind распределение, ячейки ≥2000, дистанция ≫ 338м).
- Один порог `SPEED_MIN_MPS=1.0` везде (TrustEngine-гейт + eco speed-latch).
- Типы движения `MotionKind` (STILL/WALK/BIKE/VEHICLE) с per-type accuracy для тумана (25/40/100) — сигналы надёжнее на велосипеде/машине без потери пешей точности.
- wifi/motion-BURST удерживаетACTIVE для ходьбы (окно 180с + latch 1.0 + guard от сна при MOVING).
- Счётчики всех веток TrustEngine в `counters.json`/логе дня — база для будущего «счётчики → удаление мёртвых правил».

**Non-Goals:**
- Не трогаем рендер/маску (`FogMask`, `FogRects`, `FogMaskOverlay`) — доказано здоров.
- Не вводим Activity Recognition API, новые разрешения, сервер, тумблеры эко.
- Не меняем геометрию кисти/коридоров, ворота C (лаг/вето/хвост), watchdog/ребут, формат схемы БД (без миграции).
- Не удаляем мёртвые ветки TrustEngine в этом change — только счётчики (по решению владельца «сначала счётчики, потом снос»).
- Полевая вечерняя проверка и бамп/коммит — после APK, отдельной сессией (коммит только по команде).

## Decisions

### 1. Один порог `SPEED_MIN_MPS = 1.0` везде
TrustEngine speed-гейт и `EcoGovernor.isSpeedLatch` используют одну константу 1.0 м/с (вместо разрыва 1.0/5.0). Причина: меньше точек расхождения, пешеход/велосипед/машина ловятся одинаково рано. Альтернатива «два порога 1.0/1.5» отвергнута владельцем («один порог 1.0 везде»). 5.0 м/с больше нигде не нужен — ходьба и城市 трафик покрываются latch 1.0 с `acc≤25`.

### 2. Форма speed-гейта: `speed≥1.0 И acc≤25 → нельзя STAND, MOVING; openFog по trust`
Гейт запрещает STAND и ставит MOVING, но НЕ ставит `openFog=true` автоматически — открытие тумана остаётся за series trust (2–3 successors), чтобы один GPS-рывок не рисовал ячейку. При `acc>25` гейт не срабатывает (скорость при грязном фиксе недостоверна; точка уходит в историю trust с низким весом, в `track_points` — только если проходит per-type порог). Альтернатива «авто-openFog при speed» отвергнута: туман необратим, доверие должно расти серией.

### 3. `MotionKind`: speed+acc полосы, гистерезис ±0.3, без AR API
`STILL` <1.0, `WALK` 1.0–2.5, `BIKE` 2.5–8.0, `VEHICLE` ≥8.0. Гистерезис ±0.3 м/с от текущей границы, чтобы kind не мигал на GPS-шуме. Источник — только заявленная `speed` Fused + `acc` (тестируется на `days/2026-09-23.jsonl` без эмуляции сенсоров). Вердикт в точке остаётся binary STAND/MOVING/SUSPECT (не ломаем спеки/БД); STAND доступен только при `kind==STILL`. Альтернатива Activity Recognition API отвергнута: новые разрешения, недетерминированность, сложнее реплей. Альтернатива «binary STILL/MOVING без BIKE/VEHICLE» отвергнута владельцем («всё в этом change»).

### 4. Per-type accuracy для тумана: STILL/WALK 25, BIKE 40, VEHICLE 100
`LocationFilter`/решение об openFog используют порог по `kind` вместо единого 25. Точка хуже порога kind: не в `track_points`, не открывает ячейки, но пишется в raw + история trust с низким весом (история вердикта не слепнет на вело/машине). Точки `speed>150 км/ч` по-прежнему отбрасываются. Альтернатива «единый 25» отвергнута: GPS на велосипеде/машине даёт 30–80м и теряется коридор. Альтернатива «мягче 25/50/150» — риск шума в ячейках; взяты средние 25/40/100 по согласованию.

### 5. STAND в трек при ACTIVE/BURST, не в STANDBY
Запись STAND в `track_points` с `openFog=false` только когда профиль ACTIVE или BURST (пауза mid-trip не рвёт линию). В STANDBY подтверждённая статика по-прежнему не пишется («6 часов дома = 0 точек» сохраняем). Дистанция/время считают только MOVING (STAND-строки не накручивают км/мин — `batchDistance` фильтрует по trust/openFog как сейчас). Альтернатива «писать STAND всегда» отвергнута: ломает спеку «день дома 0 точек» и раздувает БД. Альтернатива «не писать STAND вообще» отвергнута владельцем (непрерывность линии на паузах = плюс).

### 6. Эко: окно BURST 180с, latch 1.0, guard ACTIVE→STANDBY при MOVING
`BURST_WINDOW_MS = 180_000` (согласовано с `ACTIVE_SPEED_HOLD_MS=180_000`): wifi/motion-вход получает 3 минуты плотного HIGH для набора series trust. `burstTarget` и `activeMayStandby` используют latch 1.0; `activeMayStandby` дополнительно возвращает `false` при `state==MOVING` (двойная страховка от сна в движении). Альтернатива «75с окно» отвергнута: за 75с при старом latch 5.0 пешеход не успевал. Альтернатива «окно 5 мин» — лишний расход батареи при холостом wifi-loss; 180с = компромисс, калибруется полем.

### 7. `HistPoint` несёт `speed`; счётчики веток TrustEngine — в counters/лог
`HistPoint` расширяется полем `speed` (nullable), заполняется из Fused-фикса в том же колбэке — гейт и kind работают из одной доставки без второго источника. Счётчики: `static/wake/silence/jump/teleport/turn/speed_gate/kind_*` инкрементируются при срабатывании ветки, пишутся в `counters.json` (экспорт ZIP) и в событие дня DevLog; ноль ветки видим как `0`, не как отсутствие ключа (кандидат на удаление в следующем change). Альтернатива «сразу удалить мёртвые ветки» отвергнута владельцем («сначала счётчики»).

### 8. Реплей-тест как acceptance до поля
Скрипт/unit-тест прогоняет `days/2026-09-23.jsonl` через новый TrustEngine+LocationFilter+пороги: PASS = 0× STAND при `speed≥1.0`, wifi-BURST логируется с 180с, распределение Kind правдоподобно (двор/улица не всё STILL), ячейки ≥2000 (бейзлайн 213), дистанция ≫ 338м. Это заменяет «верю на слово» до вечерней прогулки. Альтернатiva «только гейт» отвергнута (комплексная приёмка выбрана владельцем).

## Risks / Trade-offs

- [Risk] Speed-latch 1.0 чаще держит ACTIVE у стоянки на границе 1.0 → Mitigation: `acc≤25`, STAND-серия + debounce 30с + speed-hold 3 мин остаются; полевой разбор `eco_state`.
- [Risk] Per-type acc BIKE/VEHICLE шумит в ячейки (30–100м) → Mitigation: счётчики `kind_*` + rejected разбивка; при регрессе площади пороги калибруются (константы в одном месте).
- [Risk] Гистерезис kind ловит запоздалый переход на разгоне → Mitigation: ±0.3 достаточен для 1 Гц Fused; лог raw хранит speed для разбора.
- [Risk] Запись STAND в ACTIVE/BURST раздувает БД при частых паузах → Mitigation: flush-батчинг тот же, openFog=false, дистанция не растёт; дневной объём — единицы строк на паузу.
- [Risk] Окно BURST 180с прожорливее 75с при частых wifi-loss → Mitigation: холостые BURST видны в метрике, анти-флаппинг якоря остаётся; ночью wifi-loss редок.
- [Trade-off] Метрики дня «ложатся» на новый вердикт — бейзлайн 23.09 (338м/18с/213 ячеек) станет несравнимым со старыми днями; принято: диагностика честнее, чем сопоставимость.

## Migration Plan

- Без миграции БД и схемы выгрузки: `MotionKind`/счётчики/`speed` в HistPoint — только runtime + `counters.json`/лог; старые ZIP без новых ключей читаются tolerant-парсером.
- Деплой: `build-apk.bat` (релиз) → APK в `dist`; вечерняя прогулка → выгрузка track-debug → разбор `fog-*.jsonl` + `counters.json`.
- Реплей 23.09 до поля: unit/скрипт — gate на готовность APK.
- Откат: revert коммита change — поведение возвращается к текущему; данные совместимы (новые поля опциональны).
- Версия: PATCH → 1.5.1 + `CHANGELOG.md` + `docs/sessions.md` (перед коммитом, по команде владельца; `python scripts/check-version.py`).

## Open Questions

- Точные полосы WALK/BIKE (2.5) и VEHICLE (8.0) — калибровать по вечернему логу (велосипед vs медленная машина), спека фиксирует границы, код возьмёт константы с полем для подстройки.
- Окно BURST 180с vs 240с — решить по `eco_gps_ms` и числу холостых BURST за неделю после реализации (спека допускает «до 180», код — константа).
- Нужна ли отдельная метрика «STAND записан в трек» (openFog=false) для A/B линии — decide по карточке дня после первого вечера (на спеку не влияет).
