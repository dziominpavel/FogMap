## Context

См. proposal.md Why. Текущее состояние: `TrackingService.onRawLocation` считает вердикт TrustEngine синхронно, пишет в `track_points` только MOVING/SUSPECT, STAND дропает полностью, accuracy-отбросы только в счетчиках `rejected_*`. `DevLog.buildPayloadJson` запрещает lat/lon, Share в `DiagScreens` шлет только counts. `FogRepository.appendPoints` открывает туман через ворота C (`PendingGate.LAG=2`, вето возврата, stale 600с) и инкрементит материализованные счетчики. Туман монотонный: удаление трека не закрывает ячейки. Ограничения: офлайн-first, все локально, вес raw ~150КБ за 2 часа езды.

## Goals / Non-Goals

**Goals:**
- Lossless raw для replay любым будущим кодом.
- Один ZIP закрывает калибровку и перенос при переустановке.
- Импорт день-в-день без дублей day-atom с честным исчезновением косяков.

**Non-Goals:**
- Diff-UI до/после, карта-сравнение, редактор точек.
- Варнинги о гео, шифрование архива, облачный синк.
- Частичный пересчет только периода с референсами кто-открыл.

## Decisions

- **Новая таблица `raw_fixes`, не файл и не расширение `track_points`.** Почему: транзакционность с day-chunk, простой подсчет размера по дням, чистка по дате одним DELETE, экспорт читает тем же DAO. Альтернативы: файл JSONL рядом (риск рассинхрона при убийстве, два источника правды), флаг dropped в `track_points` (ломает честные `pointsCount`/дистанцию и раздувает историю).
- **Единый ZIP `meta.json + days/*.jsonl + fog snapshot + counters`.** Почему: один код экспорта/импорта на калибровку и бэкап; snapshot нужен для мгновенного restore без rebuild, raw нужен для перепрожки. Альтернативы: только raw (restore после сноса долго открывается), два режима debug/backup (два парсера, путаница).
- **Full rebuild всего тумана + пересчет счетчиков с нуля в одной транзакции.** Почему: решает проблему общих ячеек между днями (ячейка 3 открыта днями А и Б) без учета референсов; счетчики не дрейфуют. Альтернатива период-only с дельтами требует хранения кто-что-открыл, которого нет.
- **Всегда перепроживать текущим кодом, версию не блокировать.** Почему: главный loop трек + новый APK обязан работать через версии. Stored вердикты и fog из файла используются только для instant-restore, калибровка идет кодом.
- **Входы: экспорт из истории с выбором от-до, импорт системным picker, Share через chooser как в `DiagScreens`.** Почему: трековое рядом с треками, минимум нового UI, Telegram-цепочка без варнингов по решению владельца.
- **Бессрочное хранение raw + экран списка по дням.** Почему: вес копейки на dev-стадии, а калибровка старых дней без файла возможна только при живом raw. Чистка только raw не трогает туман/треки.

## Risks / Trade-offs

- [Rebuild тяжелый на большом городе] → Mitigation: dev-стадия, rebuild только по явному импорту, транзакция чанками как `insertChunked`, прогресс-бар.
- [ZIP с точными координатами уходит в мессенджер] → Mitigation: только явный Share по кнопке, фоновой отправки нет, решение владельца без варнингов зафиксировано в спеке.
- [Старые установки без raw не перепроживаются] → Mitigation: задним числом не чиним, raw пишется только вперед, в meta фиксируем код-версию начала лога.
- [Пороги в meta расходятся с кодом] → Mitigation: meta только для анализа на компе, импорт всегда кодом, mismatch не блокирует.
- [Очистка raw делает экспорт невозможным] → Mitigation: объяснение на экране хранилища, удаление только явное по дням.

## Migration Plan

- Room-миграция добавляет `raw_fixes` (индекс по дате/времени), старые данные не мигрируются, туман и счетчики не трогаются.
- Откат: удалить код записи raw и экран хранилища, таблица остается пустой без вреда, ZIP-импорт отклоняется как неизвестный файл.
- Формат ZIP версионируется `format=1`, новые поля только additive.
