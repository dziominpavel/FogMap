## Context

Мотивация — в proposal.md (Why). Технический контекст, который ограничивает подход:

- `TrackingService.start()` (`TrackingService.kt:1121`) — статическая точка входа, её вызывают `MapScreen:158`, `OnboardingScreen:123`, `BootWorker:49`, `TrackingWatchdogWorker:37`. Тело обёрнуто в `runCatching { startForegroundService(...) }` без логирования: исключение исчезает.
- `TrackingService.onCreate()` (`:132`) при `!playServicesAvailable || !canTrack` делает `stopSelf()` и выходит **до** события `service_start` (`:148`); при `RuntimeException` из `startForegroundCompat` (`:141-146`) — тоже. В обоих случаях в DevLog не остаётся ничего.
- `TrackingWatchdogWorker.doWork()` (`:27`) имеет четыре пути раннего выхода (`skip_paused`, `skip_play_services`, `skip_no_permission`, `started`) и ни один не логирует; `schedule()` (`:44`) обёрнут в `runCatching` (`FogMapApp.kt:86`, `BootWorker:42`).
- DevLog: `DevLog.i/w(tag, msg, payload)` → `LinkedBlockingQueue` → `DevLogFile` пишет `cacheDir/logs/fog-<LocalDate>.jsonl` (`DevLogFile.kt:54-62`), TTL 24 ч (`:65-71`), ротация 2 МБ (`:96-104`). API `allFiles()` уже есть. Формат строки — `ts|uptime|session|seq|tag|LEVEL|msg|json`.
- Экран `DiagDiagnosticsScreen` (`DiagScreens.kt:43`) шарит `currentFile() ?: allFiles().maxByOrNull { it.name }` — фактически всегда самый новый файл.
- FileProvider authority `${applicationId}.devlog` с `<cache-path name="devlog" path="logs/"/>` (`devlog_paths.xml`) уже покрывает весь каталог логов — для шаринга произвольного файла конфигурация не нужна.
- Состояние на момент планирования: `dist/fog-2026-09-27.jsonl` ещё существует на устройстве (TTL сработает при первом старте процесса после ~00:00 29.09), `fog-2026-09-28.jsonl` — в `dist/` локально.

## Goals / Non-Goals

**Goals:**

- Сделать каждый отказ запуска трекинга наблюдаемым: в JSONL и logcat появляется событие с исходом и причиной, а не пустое окно в таймлайне.
- Дать доступ к логам прошлых суток прямо с устройства (список + шаринг выбранного файла) без правки кода и без `run-as` (приложение установлено релизным APK).
- Сохранить текущее поведение запуска/перезапуска и приватность (координат в лог не попадают).

**Non-Goals:**

- Чинить сам watchdog или фоновый старт FGS (почему `startForegroundService` мог отказать) — отдельный change после того, как данные разделят гипотезы.
- Резать отрисовку трека по временному разрыву, править баг `loc.time` → ложные `jump`.
- Менять TTL/ротацию файлов, формат JSONL, тумблер диагностики.
- Добавлять экспорт логов в ZIP или почту — только системный share chooser, как сейчас.

## Decisions

**D1. Три новых события тегом `TRACK`, по одному на акт.**
`start_attempt` (из `TrackingService.start`: `outcome=started|start_failed`, `via`, `err_class`, `err_msg`), `service_init_skip` (из `onCreate`: `reason=no_play_services|no_permission|foreground_exception`), `watchdog` (из `doWork`: `outcome=started|start_failed|skip_paused|skip_play_services|skip_no_permission`), `watchdog_schedule` (из `schedule`: `outcome=scheduled|schedule_failed`).
Альтернативы: (а) писать всё одним событием `start` с разными `msg` — менее удобно для `grep` по `start_failed`; (б) писать в счётчики `counters.json` — счётчики материализуются flush'ем живого сервиса, а отказы интересны как раз когда сервиса нет, поэтому только DevLog. События **разовые** (на старт), поэтому лимит «не чаще одного события на flush» на них не распространяется — это оговорено в delta-спеке.

**D2. Параметр `via: String` в `TrackingService.start()`.** Значения `map` / `onboarding` / `boot` / `watchdog`. Без него отказ watchdog неотличим от отказа при открытии карты. Альтернатива — выяснить вызывающего через `Debug.getStackTrace()`: дорого и хрупко. Пять вызывающих точек правятся одной строкой; сигнатура с дефолтным значением `via = "code"` сохраняет совместимость с будущими вызовами.

**D3. Логировать и успех, и отказ, но только в точке `start()`.** Успешный повторный `start()` по уже бегущему сервису порождает `start_attempt outcome=started` (реализуется через `onStartCommand`, повторно событие не пишется — оно уже записано в `start()`). Объём: watchdog даёт ≤4 события/час, открытие приложения — единицы. Альтернатива «писать только отказы» отвергнута: без парных `started` невозможно отличить «watchdog не запускался» от «запустился и упал».

**D4. Ранний выход `onCreate` логируется ДО `stopSelf()`.** Порядок: сначала `DevLog.w("TRACK", "service_init_skip", ...)`, затем `stopSelf()`. Иначе окно между `stopSelf()` и смертью процесса может потерять строку. При этом событие `service_start` (`:148`) остаётся на месте — он означает «сервис реально поднялся», и оба события сосуществуют (первое — причина, второе — факт).

**D5. Список файлов — вторым блоком экрана «Диагностика», без изменения текущего layout-порядка.** Под строкой кнопок и перед карточкой хвоста: `LazyColumn` с строками `fog-YYYY-MM-DD.jsonl · размер · дата изменения`, тап по строке = шаринг этого файла; кнопка «Поделиться» продолжает отдавать текущий файл. Альтернативы: (а) диалог выбора — хуже для быстрого обзора; (б) отдельный экран — избыточно для временного экрана диагностики, который будет удалён вместе с change `dev-logging`. Существующие кнопки «Поделиться»/«Очистить логи»/«Назад» и хвост 50 событий не трогаем.

**D6. Приватность: в отказах только класс исключения и обрезанное сообщение.** `err_msg` обрезается до 200 символов, через `runCatching` (сообщение может отсутствовать). Никаких intent-экстров, координат и путей. Проверяется расширением `DevLogPrivacyTest`.

**D7. События пишутся через существующие `DevLog.i`/`DevLog.w` без новых полей формата.** Формат, `session`/`seq` и дублирование в logcat (`FogMap:TRACK`) достаются бесплатно. Если диагностика выключена тумблером (`DevLog.enabled=false`) — события не пишутся, как и всё остальное: это поведение «Выключение диагностики» из основного спека, мы его не обходим.

## Risks / Trade-offs

- [Отказы не запишутся, если процесс убит до записи] → события пишутся синхронно в очередь до любых `stopSelf()`/возврата; потеря возможна только при убийстве процесса в течение миллисекунд между вызовом и `queue.offer`, что уже покрыто `flushBlocking` в `onTaskRemoved`/`onDestroy`.
- [Сообщение исключения может содержать что-то лишнее] → D6: класс + обрезанное сообщение, без экстров; дополняется приватностным тестом.
- [Рост `fog-*.jsonl`] → события разовые; ротация 2 МБ и TTL 24 ч остаются, объём вырастает на КБ в сутки.
- [Экран диагностики объявлен временным] → все UI-правки живут внутри существующего `DiagDiagnosticsScreen` и удалятся вместе с change `dev-logging`; спеки `dev-logging` правятся осознанно, это дельта, а не новый спек.
- [Данные за 27.09 могут не попасть в руки] → файл удаляется по TTL при первом старте процесса после ~00:00; это ограничение сборки, а не дизайна. Сборка/установка в этот же день — условие успешного расследования, но не требование спека.

## Migration Plan

1. Реализация в рабочей копии, компиляция и unit-тесты (`:app:compileDebugKotlin`, `:app:testDebugUnitTest`).
2. Сборка и установка `build-apk.bat install` **до ~00:00 29.09** — иначе `fog-2026-09-27.jsonl` удаляется по TTL и цель «взять вчерашний лог» недостижима.
3. Открыть «Диагностику», выбрать файл за 27.09, отшарить в `dist/` для разбора.
4. Откат: revert коммита — кода в БД/формате лога, влияющего на данные, change не меняет.
