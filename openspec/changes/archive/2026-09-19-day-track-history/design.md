## Context

См. proposal.md (Why) и specs (что). Текущее состояние: `TrackingService.onCreate` всегда делает `INSERT` нового дня-чанка (`TrackRepository.startDayChunk`), поэтому каждый рестарт плодит обломок с тем же именем даты; `onRawLocation` кладет в буфер все точки с вердиктом, включая STAND (`trust=80, openFog=false`), поэтому 6 часов дома пишут тысячи строк с `fogOpened=2`, а `batchDistance` считает их джиттер за движение (`trust 80 >= TRUST_OPEN 30`). Счетчики `area_cells_day_*` уже существуют и могут служить дельтой дня без новой таблицы (у ячеек `visited_cells` метки времени нет). Ограничения: без breaking-миграции БД (версия 5), старые обломки не трогаем, flush-батчинг (15 сек / 20 точек) и ворота C (`PendingGate.LAG=2`) не меняем.

## Goals / Non-Goals

**Goals:**
- Один день — одна строка трека при любом числе рестартов; полночь режет детерминировано.
- Ноль строк БД за статику; дистанция/время только по движению.
- Карточка дня читает линию + дельту + диагностику из существующих структур.

**Non-Goals:**
- Миграция/склейка старых обломков (лежат как есть).
- Неделя/месяц как представления (следующий чендж).
- Регидратация `trustHistory` из БД после убийства (сознательно откладываем).
- Изменение геометрии кисти/коридоров и порогов `TrustEngine`.

## Decisions

### D1. Find-or-create дня по дате вместо INSERT на старт
При старте сервиса и при ролловере полуночи сначала `SELECT` строки текущего дня (по диапазону `startedAt` за дату в системной зоне), только при отсутствии — `INSERT`. Имя — дата («18 сентября») как сейчас.
Альтернатива — детерминированный ключ/ID окна: отвергнута, требует миграции PK и ломает старые строки. Выбранный вариант не трогает схему и оставляет обломки прошлого нетронутыми.

### D2. Ворота статики в `onRawLocation`, до буфера
После вердикта `TrustEngine`: если `state == STAND` — точка дропается из персистентности (не кладется в `buffer`, не считается в `rejected`). Движок при этом шагает как раньше (`trustPrev` и in-memory `trustHistory` обновляются, включая дропнутые STAND): иначе холодный старт никогда не выйдет из STAND (первая точка всегда STAND при пустой истории). `countReject == jump` продолжает писаться как недоверенная точка (текущее поведение для прыжков сохраняем).
Альтернатива — ворота в `FogRepository` (писать, но не открывать): отвергнута, не решает раздувание БД. Побочный эффект выбранного: возобновление движения после долгой статики дает большой `dt` и срабатывание `afterSilence` (сброс доверия, первая точка туман не открывает) — это желаемый консерватизм.

### D3. Дистанция/время — суммой по flush-батчам движения
`batchDistance` не меняем: после D2 STAND-точек в батчах нет, фильтр `trust >= TRUST_OPEN` уже дает движение. `timeS` остается суммой `(last-first)/1000` по непустым батчам; пустые flush-и (`starved`) ничего не пишут, поэтому паузы между поездками внутри дня в сумму не попадают. Отдельный аккумулятор времени движения не вводим.
Альтернатива — явный учет MOVING/STAND сегментов по вердиктам: отвергнута как избыточная при дропе статики.

### D4. Дельта дня = существующий счетчик `area_cells_day_<дата>`
Карточка дня читает дельту из материализованных счетчиков, инкрементируемых в той же транзакции `appendPoints`. Нового хранилища «ячейки по дням» не создаем (у `visited_cells` нет времени, добавлять его — миграция и раздувание).
Альтернатива — метка времени на ячейках: отвергнута (миграция, индекс, выигрыш только для будущих spatial-запросов).

### D5. Пустые дни материализуем строкой с нулями
Строка дня создается при старте сервиса на текущую дату (даже до первой движущейся точки) и при ролловере полуночи для новой даты; если за день движения не было, строка остается с `distanceM=0, pointsCount=0`. Дни, когда сервис вообще не стартовал (телефон выключен), строк не имеют — список их не показывает, это accepted gap.
Альтернатива — синтез пропусков в UI по календарю: отвергнута, усложняет список/счетчик и рассинхронизирует «Треки» со строками.

### D6. Полночь режет, межсуточная сшивка — только кругами по концам
Новый день стартует без хвоста (`lastPoint` прошлого дня не подтягиваем — как сейчас). Коридор `cellsForSegment` длиннее `CORRIDOR_LINK_MAX_M` и так вырождается в круги, дырки на границе не возникает: каждая сторона открывает свой конец. Дистанция через полночь не переносится.

### D7. История доверия после рестарта — холодный старт (осознанно)
`trustPrev`/`trustHistory` остаются in-memory и после убийства теряются; продолжение того же дня начинается с `TRUST_START` без открытия тумана на первых точках + лаг `PendingGate`. Это консервативно (не открываем лишнего) ценой потери 20–30 сек тумана после каждого убийства. Регидратацию из хвоста БД не делаем в этом чендже.

## Risks / Trade-offs

- [Risk] Холодный старт доверия после рестарта съедает первые точки движения → Mitigation: accepted (безопасность тумана важнее); следующим ченджем возможна регидратация хвоста.
- [Risk] Микродвижение внутри 25 м (сад, двор) классифицируется STAND и дропается — реальный, но мелкий туман не откроется → Mitigation: accepted; кисть 15 м от таких точек давала бы шум, а не прогресс деревни.
- [Risk] Гонка полуночи: flush в 23:59:59 vs 00:00:01 → Mitigation: проверка даты внутри транзакции flush перед записью (как сейчас `chunkDate`), батч никогда не пишется в неверный день.
- [Risk] Пустые строки копятся (365/год) → Mitigation: trivial (строка без точек ничего не весит); счетчик «Треки» растет и дома — так задумано (один в один со списком).
- [Risk] Старые inflated `all`-счетчики (км/джиттер прошлого) остаются в тоталах → Mitigation: accepted, историю не переписываем; честные значения накапливаются с даты релиза.
- [Risk] День из 1 точки (одиночный прыжок, прошедший ворота) создаст строку → Mitigation: accepted; ворота jump уже режут грубое, порог значимости докрутим отдельно при боли.

## Migration Plan

- Миграции БД нет (схема и версия без изменений). Деплой — обычный релиз.
- Старые треки-обломки и счетчики остаются как есть; новое поведение применяется только к новым записям.
- Откат — предыдущий APK: новые строки дней читаются старым кодом как обычные треки (совместимо вперед/назад на уровне схемы).

## Open Questions

- Регидратировать ли `trustHistory`/`trustPrev` из хвоста точек дня после убийства, чтобы не терять 20–30 сек тумана? Не меняет спеки, только качество открытия; решить следующим ченджем по полевым замерам.
- Что показывать как длительность дня из 1 точки (0 мин vs «<1 мин»)? Чисто UI-формат, спеки не меняет.
- Создавать ли пустые строки за дни, когда сервис ни разу не стартовал (телефон был выключен)? Сейчас — нет; календарный синтез остается опцией будущего.
