## Context

См. `proposal.md` — Why. Факты rebuild 21.09 новым кодом (`1.2.0.23-gd0b7a48`), на которых стоят решения:

- `importAndRebuild` (`TrackDebugImport`): `parseZip` игнорирует `counters.json`, `reprocessDay` перепроживает raw текущим кодом, чанки по 20 штук идут в `appendPoints`, затем `recordRejected`. `recordEco` не вызывается никогда — после импорта эко-карточка пустая (`eco_fix=5` от одного живого flush).
- Правило «снимок fog/counters не используется» зафиксировано в докстринге `TrackDebugImport` — его придётся сузить.
- `time_s` считается как `last.time − first.time` чанка (`FogRepository.appendPoints`): живые батчи ограничены ~15 с таймером, rebuild-чанки — только количеством (20), чанк через дыру 09:16→12:25 внёс ~3 часа (итог 38170 с вместо ~2700 с).
- Подозрение на двойной счёт живого `flush`: счётчик 19.59 км не выводится из сохранённых 276 точек (строгий пересчёт — 11.24 км), а rebuild теми же правилами дал 11.36 км ровно по счётчику. Кандидат — конкурентные запуски `flush` (таймер 15 с + `launch { flush() }` при переполнении буфера).
- Эко-метрики — свойства живой сессии (каденс доставки, GPS-время, якоря пробуждений), а не геометрии: из raw их честно не восстановить (в STANDBY писалась каждая 6-я точка, якорей в raw нет).

## Goals / Non-Goals

**Goals:**
- После импорта эко-карточка дня совпадает с живой (медиана, разрывы, счётчики).
- `time_s` после rebuild вменяемый; живые счётчики сходятся с пересчётом из точек.
- Без миграций БД; старые выгрузки импортируются как раньше (деградация к «нет данных»).

**Non-Goals:**
- Не меняем геометрию тумана, ворота C, TrustEngine, пороги EcoGovernor.
- Не боремся с заморозкой процесса на уровне ОС.
- Не переносим `rejected_*`, `tracks_*`, дистанцию/время/площадь из снимка — они пересчитываются из raw как раньше.

## Decisions

### 1. Эко-метрики при импорте — восстановление из снимка, а не пересчёт
`parseZip` начинает разбирать `counters.json` (тот же tolerant-подход: битые строки пропускаются, неизвестные ключи терпим), `importAndRebuild` после пересчёта геометрии пишет эко-ключи (`ECO_METRICS`) за импортированные дни теми же значениями через `recordEco` с явной датой. Пересчёт из raw отвергнут: из-за семплирования 1/6 он занижает fix/stand, а префикс от якоря невосстановим в принципе (якорей в raw нет). Геометрия (точки/туман/дистанция/время/отбросы) по-прежнему пересчитывается из raw — правило «снимок не используется» сужается до геометрии, докстринг правится.
- Старые выгрузки без новых ключей: недостающее = отсутствие данных (нули в counters + карточка показывает «нет данных» медианы, а не 0).
- Диапазон: восстанавливаются ключи дней из диапазона выгрузки (`day_*` + соответствующие `week_*`/`all` как в снимке); счётчики перед rebuild уже обнулены, двойного счёта нет.

### 2. Чанки rebuild ограничены временем
Нарезка принятых точек: чанк закрывается при 20 штуках ИЛИ когда спан превысил ~120 с — следующий чанк начинается с новой точки. Хвост ворот C (`TAIL_LIMIT=32`) покрывает чанк 20 + лаг как раньше, поведение гейта не меняется. Альтернатива «резать только по дырам > N минут» отвергнута: порог 120 с проще и покрывает все случаи одним правилом.

### 3. Сериализация `flush` мьютексом
`private val flushMutex = Mutex()` вокруг тела `flush()` (после чтения буферов — нет, вокруг всего включая транзакцию: пересекаться не должно ничего). Best-effort пути (`onTaskRemoved`/`onDestroy` через `flushBlocking`) при занятом мьютексе пропускают запись: `runBlocking` на главном + занятый мьютекс = риск дедлока до таймаута, а путь и так best-effort. Проверка эффекта — сверкой счётчиков с пересчётом из точек (как вскрылось 19.59 vs 11.24), а не unit-тестом на гонку.
- Альтернатива «флаг isFlushing» отвергнута: мьютекс честнее держит и suspend-пути, и блокирующий путь.

### 4. Дистанция — от хвоста дня, якорь — только коридор (по следам отчёта выше)
`appendPoints` берёт `prev` для `batchDistance` из последней записанной точки дня, а `wakeAnchor` идёт только в `confirmPending` (коридор тумана + adjudication) и в метрику префикса. Выбор оформляется чистой `planBatch(dayTail, wakeAnchor)` — контракт «хвост для дистанции ≠ якорь для коридора» тестируется без БД. Альтернатива «выкинуть якорь из `appendPoints` совсем» отвергнута: коридор от якоря — осознанная фича wake-balance-parking, ломать её нельзя. Побочный эффект: дистанция дня больше не включает хорды (21.09: 19.59 км → ожидаемо ~11.4 км).

## Risks / Trade-offs

- [Восстановление эко из снимка переносит и «плохие» старые значения] → это те же числа, что показывала карточка до импорта; честно, предсказуемо.
- [Снимок покрывает не все дни БД] → восстанавливаем только дни диапазона; остальные дни эко-метрик не имеют (как сейчас после любого импорта).
- [Мьютекс чуть сериализует flush при шторме точек] → flush и так короткий (десятки мс, slow > 500 мс логируется); конкуренции в норме нет.
- [`tryLock`-пропуск в `flushBlocking` может потерять последнюю пачку при убийстве] → потери и сейчас ограничены интервалом; best-effort по построению.
- [Двойной счёт мог идти не из конкуренции flush] → задача начинается с подтверждения гипотезы сверкой (пересчёт из точек vs счётчик на живых данных); если не подтвердится — фиксируем вывод, мьютекс всё равно оставляем как гигиену.

## Migration Plan

- Миграций БД нет: новые чтения `counters.json` толерантны, старые выгрузки импортируются.
- Раскатка: сначала подтверждение гипотезы двойного счёта + мьютекс, затем чанки по времени, затем восстановление эко.
- Полевая проверка: повторный импорт дня 21.09 — эко-карточка совпадает с живой, `time_s` вменяемый, дистанция сходится с пересчётом.

## Отчёт: полевая сверка гипотез (21.09, после rebuild)

Числа (выгрузки до/после rebuild одного и того же raw):

- живой счётчик дня до rebuild: `distance_cm_day_2026-09-21 = 1 959 805` (19.60 км) при 276 точках;
- строгий пересчёт из этих же 276 точек (`trust >= 30` с обеих сторон): 11.24 км; полный путь по всем парам точек: 11.66 км;
- rebuild того же raw новым кодом (без wake-якоря): счётчик 11.36 км и совпадает с пересчётом.

Вывод: расхождение в 1.7 раза подтверждено, но **причина не конкурентный flush**:

- буфер читается и очищается под `synchronized(buffer)`, а `prev` для дистанции читается внутри транзакции — транзакции Room сериализованы, пересечься батчи не могут;
- объяснение — wake-якорь: `appendPoints(..., wakeAnchor)` использует якорь как `prev` для `batchDistance`, поэтому в дистанцию попадает хорда «якорь → первая точка». В тот день сумма префиксов 13.9 км при крупных разрывах 5.7 км, а 19.60 − 11.36 = 8.24 км — эта разница.

Следствие: мьютекс остаётся как гигиена, а сходимость счётчиков потребовала отдельной правки в этом же change (решение 4): дистанция считается от последней записанной точки, а якорь используется только для коридора тумана и метрики префикса. Ожидаемый эффект правки 1.3 на дне 21.09: дистанция ≈ 11.4 км вместо 19.59 км.
