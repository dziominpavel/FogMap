## Context

Мотивация — в proposal.md. Технический контекст текущей реализации:

- `data/SettingsRepository.kt`: `ThemeModes { DARK, LIGHT, SYSTEM, DEFAULT = DARK }`, ключ DataStore `theme_mode`, `setThemeMode` валидирует `require(v in {dark, light, system})`, поток `themeMode` отдаёт сохранённое значение или дефолт.
- `ui/theme/Theme.kt`: `FogMapTheme(themeMode)` выбирает цветовую схему через `when`: `LIGHT -> false`, `DARK -> true`, `else -> isSystemInDarkTheme()`; тот же принцип в чистой функции `isDarkTheme(themeMode, systemDark)`.
- `ui/screens/SettingsScreen.kt:80-98`: `SingleChoiceSegmentedButtonRow` с тремя опциями (Тёмная / Светлая / Система).
- Потребители системного режима помимо оболочки: `MapScreen.kt:120-125` (ночная карта MapKit и veil-цвет `FogMask.VEIL_DARK/VEIL_LIGHT`) и `HistoryScreens.kt:337-340` (мини-карта трека в деталях) — оба вызывают `isDarkTheme(mode, isSystemInDarkTheme())`.
- `MainActivity.kt:31-33`: поток `themeMode` из `SettingsRepository` → `FogMapTheme`; смена темы идёт рекомпозицией, без перезапуска (это поведение сохраняется).
- `res/values/themes.xml`: платформенная тема `DeviceDefault.DayNight`, но статусбар/навбар/фон окна явно закрашены `splash_background` (`#FF0F1419`, тёмный в обоих режимах, чтобы не мигал белым). DayNight влияет только на атрибуты, не переопределённые явно.
- Тестов на тему нет ни в `app/src/test`, ни в `app/src/androidTest`.
- Контракт витрины (`store.yaml` FogMap) тему не упоминает — требование живёт только в `app-shell`.

Аналогичный переход уже выполнен витриной `dziominpavel.github.io` (change `redesign-storefront`): двухрежимность, миграция `system`→`dark`, дефолт `dark`. Паттерн переносится с поправкой на Android/DataStore вместо localStorage.

## Goals / Non-Goals

**Goals:**
- Ровно два режима темы: `dark` (дефолт) и `light`; режим `system` исчезает из UI, валидации и логики применения.
- Пользователи с сохранённым `system` получают `dark` без действий со своей стороны (миграция при чтении).
- Night-карта, veil и мини-карта трека следуют выбранной пользователем теме, а не системной.
- Поведение без перезапуска, дефолт `dark`, отсутствие «нечего выбрано» в сегменте настроек — сохраняются.

**Non-Goals:**
- Не меняется визуальный дизайн обеих тем (токены, палитры `FogDarkColors`/`FogLightColors`, `FogMask`).
- Не трогается `res/values/themes.xml` (платформенный DayNight и тёмный сплэш-фон) — он не следует пользовательскому выбору темы и остаётся как есть.
- Не вводится новый режим и не добавляется следование `prefers`/системе как «тихий третий» вариант.
- Не меняется хранение (тот же DataStore-ключ `theme_mode`) и не добавляется версионирование схемы настроек.
- Витрина `dziominpavel.github.io` не затрагивается — там двухрежимность уже реализована.

## Decisions

### D1. Миграция `system` → `dark` при чтении, без отдельного «разового» прохода

Единственная точка истины — функция чтения значения темы: значение из хранилища нормализуется по правилу `light` → `light`, всё остальное (включая `system` и мусор) → `dark`; нормализованное значение тут же перезаписывается в DataStore.

*Почему так:* зеркалит проверенное решение витрины (`theme.js: read()` с перезаписью), покрывает все потоки чтения (MainActivity, экраны) одним изменением и гарантирует, что после первого чтения в хранилище лежит только `dark`/`light`.

*Альтернативы:*
- Разовый миграционный `store.edit` при старте приложения — отклонено: требует отдельной точки вызова (Application.onCreate + coroutine), легко пропустить при чтении из других мест, два источника правды.
- Оставить `system` в хранилище, но трактовать как `dark` без перезаписи — отклонено: хранилище навсегда остаётся «грязным», UI сегмент не найдёт выбранной кнопки, пока перезапись не случится.
- Явная ветка миграции в `SettingsRepository.themeMode` + UI-фолбэк — отклонено: дублирование, риск рассинхрона.

### D2. `ThemeModes.SYSTEM` и вторая функция `isDarkTheme` удаляются; сигнатура упрощается

`ThemeModes` остаётся с `DARK`/`LIGHT`/`DEFAULT = DARK`; `setThemeMode` валидирует `require(v in {dark, light})`. `isDarkTheme(themeMode: String): Boolean` теряет параметр `systemDark` и становится проверкой `themeMode != LIGHT` (с учётом нормализации D1 аргумент всегда `dark`/`light`). Ветка `else -> isSystemInDarkTheme()` в `FogMapTheme` заменяется на `themeMode != LIGHT`; импорт `isSystemInDarkTheme` удаляется из `Theme.kt`, `MapScreen.kt`, `HistoryScreens.kt`.

*Почему так:* после D1 системное состояние недостижимо — второй аргумент становится мёртвым кодом, а три вызова с `isSystemInDarkTheme()` — точками возврата режима. Одно правило «не `light` ⇒ тёмная» не оставляет путей для расхождения.

*Альтернативы:*
- Оставить `isDarkTheme(mode, systemDark)` с фиксированным `systemDark = false` — отклонено: ложная гибкость, читается как «система ещё может учесться».
- Сделать `isDarkTheme` расширением `String` — отклонено: проект уже держит её как top-level функцию в `ui/theme/Theme.kt` с существующими импортами; переименование без benefit.

### D3. Ночная карта и veil читают тот же нормализованный режим

`MapScreen` и `HistoryScreens` продолжают читать `THEME_MODE` напрямую из DataStore-потока (как сейчас, из уже существующих `paused`/`detailPrefs`), но через упрощённый `isDarkTheme(mode)` без `isSystemInDarkTheme()`. Решение о смене карты day/night и veil остаётся синхронным с оболочкой.

*Почему так:* минимальное изменение — экраны уже подписаны на тот же поток; переносить чтение в `SettingsRepository.themeMode` не нужно, нормализация в месте чтения (D1) покрывает и прямое чтение ключа.

*Альтернатива:* собрать единый `StateFlow<Boolean> isDark` в репозитории и подписывать на него карту — отклонено: шире скоуп (новый API репозитория), чем нужно для удаления режима; можно сделать позже отдельным рефактором.

### D4. UI настроек: две кнопки в том же `SingleChoiceSegmentedButtonRow`

Опции `listOf(DARK to "Тёмная", LIGHT to "Светлая")` — структура и поведение сегмента не меняются, убирается только третий элемент и его `SegmentedButton`.

*Почему так:* сегмент с двумя элементами работает корректно (`itemShape` считает от `options.size`), дизайн-система экрана не требует замены компонента.

*Альтернатива:* переключатель `Switch` или выпадающий список — отклонено: меняет UX без запроса, увеличивает площадь изменений и риск визуальной регрессии.

### D5. Платформенный `themes.xml` остаётся без изменений

`DeviceDefault.DayNight` + явно закрашенный тёмный `splash_background` не участвуют в пользовательском выборе темы: Compose-слои перекрывают их после создания окна, а статусбар/навбар держат фиксированный тёмный цвет в обоих режимах (так было и до change).

*Почему так:* замена DayNight на не-DayNight не меняет наблюдаемого поведения (все видимые атрибуты явно заданы), но создаёт риск регрессии шторок/сплэша без выигрыша. Если когда-нибудь шторки решат привязать к выбранной теме — это отдельный change.

## Risks / Trade-offs

- [У установленных пользователей лежит `system`, и после обновления они «молча» получают тёмную вместо системной] → это осознанный результат (BREAKING описан в proposal); миграция D1 перезаписывает значение, сценарий «Миграция устаревшего системного режима» в дельте фиксирует ожидание.
- [Прямое чтение ключа в `MapScreen`/`HistoryScreens` обходит нормализацию репозитория] → нормализация выполняется в функции чтения (D1), через которую проходят оба экрана; плюс `isDarkTheme` трактует любое не-`light` как тёмное — двойная защита.
- [Кто-то из будущих вызовов снова передаст `isSystemInDarkTheme()`] → компилятор откажет: функция теряет параметр `systemDark`, импорт удаляется; grep-проверка в задачах на `prefers`/`isSystemInDarkTheme`/`ThemeModes.SYSTEM`.
- [Сегмент с двумя кнопками выглядит иначе на узких экранах] → существующий `SingleChoiceSegmentedButtonRow` адаптивен, ручной проход настроек на 360px входит в гейт-чек-лист задач.
- [Отсутствие тестов на тему] → минимальный unit-тест на нормализацию и `isDarkTheme` добавляется в задачах; поведение UI проверяется браузерно-аналоговым ручным гейтом (сборка + установка).

## Migration Plan

1. Код с нормализацией (D1) и двумя режимами выходит одной сборкой; старые данные в DataStore мигрируют при первом чтении, откат на предыдущий APK безопасен (старый код прочитает `dark`/`light` и продолжит работать — значения совместимы).
2. Отдельных флагов, серверных ступеней и координации с витриной нет: change полностью локален в FogMap.
3. Rollback — установка предыдущего APK из `dist/archive/` (значения `theme_mode` обратно совместимы).
