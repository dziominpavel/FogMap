## Context

См. proposal.md (Why): дыра 12:00-13:00 — сервис не был жив, рестарт произошел только в 13:27 при открытии приложения. Текущие стартеры: MapScreen (`DisposableEffect` + `TrackingService.start`) и BootReceiver/BootWorker. Watchdog отсутствует. Буфер точек — RAM, flush 30 сек / 20 шт, при убийстве потери до 30 сек молча. `TrackEntity.distanceM/pointsCount/finishedAt` не обновляются никогда (вечные 0 км). Отбросы (`LocationFilter`) молчаливые.

## Goals / Non-Goals

**Goals:**
- Дневные дыры от убийства процесса исчезают: watchdog + START_STICKY + рестарт подписки.
- Потери буфера ограничены и видимы: короткий flush + best-effort сброс.
- Каждый отброс объяснен: причина + счетчик + состояние GPS.
- История честная: дистанция/время/точки обновляются при flush.

**Non-Goals:**
- Нарезка на поездки (один трек = одна жизнь сервиса сохраняется) — следующий чендж.
- Смена фильтров и радиусов — следующий чендж.
- Смена сетки и рендера — третий чендж.

## Decisions

- **Watchdog через WorkManager (periodic, expedited fallback) поверх START_STICKY, а не вместо.** Альтернатива — только START_STICKY: отклонено, на API 34+ и OEM (Xiaomi/Huawei) липкий рестарт location-FGS из фона запрещен/душится; периодическая проверка — санкционированный путь. BootReceiver/BootWorker остаются первым рубежом.
- **Flush короче + сброс в `onDestroy`/`onTaskRemoved` best-effort, а не персистентный буфер.** Альтернатива — писать каждую точку сразу в БД: отклонено, лишние транзакции и пробуждения; альтернатива — персистентная очередь: избыточно для одного интервала, оставляем RAM + короткий интервал + best-effort.
- **Обновление трека в той же Room-транзакции, что и вставка батча (`appendPoints`).** Причина — атомарность "точки = статистика трека"; иначе рассинхрон дистанций (нынешний баг). Новые `TrackDao.updateStats` вызываются внутри транзакции.
- **Счетчики отбросов — материализованные (`rejected_<reason>_<suffix>` day/week/all), как существующие счетчики.** Причина — консистентность с архитектурой статистики (ЧП-5), мгновенное чтение без пересчета.
- **Состояние GPS — read-only производное от последних событий (последняя принятая/отброшенная точка + время), без хранения истории событий.** Причина — достаточно для индикатора "пишет / GPS плохой / молчит", полная история — избыточна.

## Risks / Trade-offs

- [Risk] OEM все равно душит watchdog (агрессивные батареи) → Mitigation: честный экран онбординга батареи уже есть; watchdog снижает, а не убирает зависимость; диагностика покажет "сервис убит в X", что само по себе ответ.
- [Risk] Частый flush ест батарею → Mitigation: интервал подбирается замером (кандидат 10-15 сек вместо 30), пачки сохраняются; персистентность на каждую точку не вводим.
- [Risk] Двойной старт сервиса (MapScreen + watchdog одновременно) → Mitigation: идемпотентный `start` (сервис уже бежит — no-op), один `trackId` на жизнь сервиса.
- [Risk] Счетчики отбросов растут бесконечно при лежании в офисе → Mitigation: это и есть правда; уплотняем по day/week/all как остальные, UI показывает компактно.
